- 目标：把评测中心从“指标与事件展示器”重构为“发布决策与证据审阅工作台”

## 1. 问题定义

当前界面已有完整的数据采集、实时 SSE、检索/工具/任务/judge 指标、trace 与 baseline
信息，主要问题集中在信息架构和视觉表达：

1. 首屏没有优先回答“能否发布”，门禁、阻塞项和 baseline 差异不够突出。
2. 指标以同权小卡片平铺，缺少阈值、置信区间、样本数和分子/分母。
3. 单样例默认展示固定布局流程图，节点字号小、资源 chip 密集，阅读成本高。
4. badcase 位于报告底部，无法从问题结论直接下钻到失败链和原始证据。
5. “透明”主要依赖展开原始 payload，缺少 `结论 → 影响 → 样本 → trace` 的逐层路径。

## 2. 设计原则

1. **决策优先**：先展示发布门禁、blocker/warning、核心指标变化，再展示明细。
2. **案例优先**：badcase 是主入口；每个问题必须包含影响范围、证据和下一步动作。
3. **时间线优先**：单次运行默认用共享时间轴表达阶段、耗时、工具调用、重试和降级。
4. **逐层透明**：概览给结论，案例给依据，轨迹保留原子事件与原始 payload。
5. **克制表达**：正文不小于 12px；颜色只表达通过、警戒和阻塞；减少嵌套卡片。
6. **数据口径不降级**：保留现有 API、SSE、指标计算和 trace 字段，重构以展示层为主。

## 4. 验收标准

1. 首屏无需滚动即可看到发布门禁、阻塞项数量和核心指标 verdict。
2. 每个核心指标同时显示当前值、baseline、变化、阈值或预算、样本口径。
3. 至少一个 blocker 可以下钻到具体 QA、失败原因和 trace。
4. 单次运行默认视图在 12px 及以上字号下可完整阅读，不依赖悬停解释。
5. `npm run build:renderer` 通过；受影响的评测相关测试通过。
6. 桌面和窄屏均无文字重叠、关键内容裁切或不可操作的横向溢出。
