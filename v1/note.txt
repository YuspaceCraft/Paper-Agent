如何加载不同格式的文件
    通过 格式->加载器 的分发表，使用对应加载器加载不同格式文件。
    纯文本文件用ath.read_text，csv文件用csv.DictReader，PDF用langchain_community中的PyPDFLoader，docx用docx2txt.process

文件切块策略选择
    不同格式文件采用不同切块策略
    纯文本文件按chunk_size，chunk_overlap来切分，设置separators，按照段落/章节/句子 递归切分天然合适。
    代码文件按照AST树感知函数与类边界
    PDF文件中表格和图表可能跨页，合并可能跨页的相邻页后用RecursiveCharacterTextSplitter按段落切分
    CSV文件不宜使用向量化直接存入向量数据库，例如问到“第4列均值”类的问题时无法处理，破坏列对齐
    根据每个文件metadata中的文件type路由到不同切分策略进行处理
    46个PDF,1个txt加载后为823个文档段
    切分完成后为7726个块

基于RAG的agent框架理解
    初始搭建框架仅包括两阶段流水线，数据层(提取，索引，存储)，检索层(检索，重排，改写)
    Agentic RAG应该再加一个代理层，包含规划，工具调用，反思循环，记忆管理。 可以类比为操作系统

代理层如何实现
    从简单到复杂
    ReAct/Function call -> Planner -> Multi-Agent

元数据污染，版权页干扰
    RAG检索时用户提出提供原文内容时，被文件中本来就有的版权、使用声明引导，导致无法返回原文内容
    解决办法
        基于规则的预处理，编写正则表达式或文本匹配脚本，在分块前删除相关关键词或语句
        PDF解析优化，使用支持版面分析的工具，识别并剔除页眉，页脚，版权声明等非正文区域


记忆管理具体如何设计
    短期记忆要做什么处理
        指代消解：用户提问模糊，需要结合对话摘要和最近对话进行重写后查询
        状态维护：每次回复前，内部更新当前任务状态。用户切换话题则归档旧节点并确认新焦点
        摘要触发：当对话轮次>8论或Token占用>60%时，自动对历史对话生成结构化摘要。
    长期记忆应该存储什么内容，检索方式如何选择
        四层存储模型：
            1.清洗后文献本体，正文，图标描述，公式等
            2.结构化知识摘要，研究问题，方法论，实验设置，核心结论，局限性。 论文格式需要统一（Method，Dataset，Metric，Conclusion）
            3.领域知识图谱，实体+关系
            4.用户个性化记忆，阅读偏好，已读清单，阅读兴趣，常用术语
        检索优先级：
            优先命中2，3层，需要验证细节或获取原文时回退1层
            个性化记忆决定回答深度与术语选择
        
    context爆炸如何处理
        接近输入token上限时
            裁剪：丢弃早期低相关性内容
            分治： 对于多文档任务，先进行逐篇总结再汇总
            外部化：将长表格公式等内容写入临时笔记
            降级处理：主动告知用户讨论内容过多，建议聚焦当前核心问题或回顾之前某个结论

json和jsonl的区别
    json是单个有效的json值，必须一次性加载并解析整个文件
    jsonl是多行文本，每行都是一个独立的合法json对象，可以逐行读取处理解析（流式处理） 并行处理，增量构建

由RAG应用到agent应用的跨越需要什么？
    RAG应用为硬编码的决策： question ->  rewrite question -> retrieve -> generate
    Agent为LLM驱动的动态路由：
        question -> LLM分析意图
        -“简单事实” -> 直接检索回答
        -“复杂对比” -> 拆分子问题 -> 多次检索 -> 综合回答
        -“需要计算” -> 调用python工具 -> 结合检索结果回答
        -“文献综述” -> 多轮迭代搜索 -> 评估覆盖面 -> 补漏 -> 生成综述
    需要具备 Tool Calling， ReAct/Plan-Execute循环， 反思和自我修正， 多步检索策略， 主动追问&澄清

系统回复设计
    Loop 控制缺陷：修正后循环未 break，重新执行时 React 模式创建全新 agent，丢失第一轮上下文
    System Prompt 以检索为中心：无论意图类型，"先检索再回答"始终是第一条规则
    修正阶段缺少执行上下文：_phase_correct 只拿到 memory 上下文，不包含当轮工具调用记录
    工具选择无意图感知：Plan-Execute 模式下纯关键词匹配，修正步骤可能被路由到 search_literature
    工具摘要器不支持文件管理工具：文件操作结果无结构化提取，反馈模糊
    Fix 1 (Loop break) → 一行逻辑改动，影响最大
    Fix 2 (Intent-aware prompt) → 最广泛的预防效果
    Fix 3 (Correction context) → 配合 Fix 1/2
    Fix 4 (Tool selection) → Plan-Execute 模式补充
    Fix 5 (Summarizer rules) → 提升整体反馈质量

任务执行反馈，上下文管理，记忆管理
分析agent中执行结构，判断是否有以下问题：
1. 用户问题意图识别过于复杂，逻辑有重复矛盾的地方。
2. 执行loop有逻辑缺陷。
3. 涉及提示词的部分过于严苛或是模糊，误导影响llm判断。
4. 记忆管理不统一，所有需要使用上下文或者记忆的地方更新/查询逻辑缺失或不完整。
5. 工具描述或功能不清晰，有混淆误导大模型的风险。
6. 反思修正部分，反思内容因为执行流程信息缺失误判，是查询记忆位置误判还是记忆缺失误判。

仅使用短期记忆与长期记忆。
长期记忆包括对每次QA内容的摘要，按结构化存储。
短期记忆包括最近5-8次的对话记忆，采用LRU策略，对话记忆按照结构化存储，包含
任务栈：显示维护当前目标、子目标分解及完成状态。每执行一步，agent首先确认检索此栈，确认“我现在应该做什么”，而非“我上一句说了什么”。
观察缓冲区：仅保留最近N步的工具返回结果和环境反馈，并自动摘要旧结果。防止冗余信息淹没关键线索。
全局约束/规则区：将System Prompt中的核心限制作为常驻记忆，每次推理前强制注入上下文，对抗“指令遗忘”。
反思/纠错日志：记录之前的失败尝试和自我修正结论。当遇到类似困境时，优先检索此日志而非重新试错。
ReAct 范式： 强制模型输出 Thought → Action → Observation 三元组。Thought 字段就是显式的“思考槽”，要求模型在行动前必须先陈述理由、评估当前状态与目标的差距。这迫使模型利用短期记忆中的最新 Observation 进行即时推理，而非机械执行预设流程。
自我反思/Reflexion： 在 Action 失败或得到模糊结果时，触发专门的“反思步骤”。Agent 会回顾短期记忆中的失败轨迹，生成自然语言形式的“经验教训”写入反思日志，再基于此规划下一步。这将“试错”转化为“学习”。
计划-执行-验证闭环： 对于复杂任务，先生成显式计划并存入任务栈；每执行一步后，增加一个“验证步骤”，比对当前结果与计划预期。若偏差超过阈值，立即暂停执行、回滚或重规划，而非盲目继续。
